## HANDOFF 方案 vs 实际实现核对
- 核对 HANDOFF.md（移动端海拔方案调研）与实际代码是否一致。
- 结论：**核心路线符合，气压计融合层缺失**。
  - ✅ GPS + 本地 EGM96 离线转 MSL 已跑通：Android `LocationProviderAndroid.cpp` 用 `GeographicLib::Geoid::ConvertHeight(ELLIPSOIDTOGEOID)`，`egm96-5.pgm`(18MB) 打包 assets、运行时拷内部存储、纯离线，满足高海拔无网络约束。macOS `CLLocation.altitude` 本身即 MSL 不重复转换。
  - ✅ 正确避开 HANDOFF 记录的坑（椭球高≠海拔、平台差异、排除在线 API）。
  - ❌ 气压计融合完全未实现：无传感器读取/相对高度追踪/校准锚点/滤波；`LocationData` 无气压字段；`AltitudeDisplay.cpp:635` 的 "-- mmHg" 是写死占位符。
  - ⚠️ 技术栈选型偏离但合理：最终用 C++20 native + GeographicLib，而非 HANDOFF 分析的 egm96-universal(JS)。
- 后续若补全 HANDOFF 方案，需实现：气压计接入 → 相对高度 → GPS+EGM 锚点校准（可选互补/Kalman 滤波）。

## 气压计融合层开发（已实现）
按 HANDOFF 推荐方案落地气压计融合层，新增/改动文件：
- `Backend/LocationProvider.h`：LocationData 增 `pressureHPa/fusedAltitude/climbRate/hasPressure` 字段。
- `Backend/PressureProvider.{h,cpp}`：跨平台气压计抽象 + 工厂（macOS 返回 nullptr，未来 iOS 走 CMAltimeter）。
- `Backend/PressureProviderAndroid.cpp`：NDK `ASensorManager`（ASENSOR_TYPE_PRESSURE）独立线程采样，10Hz，零权限、不改 Kotlin。无气压计设备 isAvailable()=false 降级。
- `Backend/AltitudeFusion.{h,cpp}`：纯 C++ 融合器。国际气压高度公式 h=44330*(1-(P/P0)^(1/5.255))；气压 EMA 去抖；互补滤波(α=0.98) 融合气压增量与 GPS 绝对海拔；P0 由达标 GPS(精度≤20m) 反解并 EMA(0.02) 慢校准抗天气漂移；无 GPS 时纯气压航位推算；垂直速率差分+EMA。无气压计时 fusedAltitude 回退 altitudeMSL（零回归）。
- `Backend/Backend.{h,cpp}`：持有 pressure+fusion，新增 `currentFused()`（Frontend 每帧 pull）、`hasBarometer()`。
- `Frontend/Frontend.cpp`：改用 `Backend::currentFused()`。
- `Frontend/AltitudeDisplay.cpp`：主显示改 fusedAltitude；顶部信息行真实气压(hPa→mmHg)；详情区加 GPS海拔/融合海拔/气压/垂直速率。
- 架构关键：UI 传空回调，数据流是每帧 lastKnown() pull，故融合中枢放 Backend，每帧 pull 而非事件驱动，无额外锁。
- macOS releasedbg 构建通过（仅 spdlog fmt deprecation 第三方告警）。调参入口在 AltitudeFusion.cpp 匿名 namespace 常量。
